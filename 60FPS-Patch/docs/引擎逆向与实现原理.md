# 《命令与征服3：凯恩之怒》120 FPS 运行时动画补丁 —— 逆向分析与实现报告

> 目标：在不改变原游戏速度、原动画速度的前提下，把运行时动画帧率提升到 120 FPS。
> 结论：已实现并在本机验证。渲染 118.8～120 FPS，逻辑 tick 15.20 次/秒（原版 15.20），
> 逻辑帧率常量仍为 15，游戏速度与动画速度不变；动画在逻辑 tick 之间做连续插值，因此
> 视觉上是 120 FPS 的平滑动画。

> **交付版本（2026-11-08 修复）**：`CnCFpsUnlocker.dll` 为 `1.9.5-kw1.0-drawfix`，
> 在上游 1.9.5 基础上增加 1.0 版本的 `isNewTick` split 识别，修复“电脑阵营步兵/坦克
> 完全不显示”的问题。详见 [`修复说明-单位不显示.md`](修复说明-单位不显示.md)。

> **60 FPS 版说明**：本报告以 120 FPS 模式为例撰写。60 FPS 版使用同一个
> `CnCFpsUnlocker.dll`，仅 `SAGEUnlocked.ini` 的 `fps=60` 不同，补丁地址与引擎原理完全一致；
> 60 FPS 的实测数据见同目录 `60fps验证.md`。

## 3. SAGE 引擎计时架构（静态逆向结果）

### 3.1 两个独立的帧率常量

在 `.data` 中紧邻的两个全局整数：

| 地址 | 含义 | 原值 |
|---|---|---|
| `0xB72ADC` | 逻辑帧率（logic FPS） | **15** |
| `0xB72AE0` | 渲染帧率（render FPS） | **30** |

这与 SAGE 的经典设计一致：**逻辑 15 Hz，渲染 30 Hz**，原版每个逻辑 tick 渲染 2 帧。
游戏速度由逻辑 tick 决定，渲染帧率只影响画面平滑度。因此“只改渲染侧、不改逻辑侧”
是保持原速度的关键。

### 3.2 主循环 `sub_5836E5`

IDA 反编译出的主循环（节选，变量名为分析标注）：

```c
while ( !*((_BYTE *)this + 28) )              // this = GameEngine
{
    (*(void (__thiscall **)(_DWORD *))(*this + 20))(this);   // vtable+0x14：每帧更新

    // ---- 帧限制器 ----
    Time = timeGetTime();
    // 帧间隔 = 1000 / (renderFps * gameSpeed)
    v15 = (unsigned __int64)(flt_BE51FC / ((double)(int)this[89] * *(float *)&dword_B6FC0C));
    while ( Time - dword_BE4F6C < v15 )
        Time = (Sleep(0), timeGetTime());

    // ---- 以 64 帧滑动平均反推实测 FPS，再夹在 [logicFps, renderFps] ----
    v18 = this[87];
    v19 = (v18 <= 0) ? dword_B72AE0 : 64000 / v18;
    ...
    v20 = 10 * v19 / dword_B72ADC;            // 10 * fps / logic
    this[89] = v20 / 10;                      // 更新下一帧的帧率估计
}
```

对应的汇编（`0x583A2F` 起）：

```asm
00583A2F  call    j_timeGetTime
00583A34  fild    dword ptr [esi+164h]        ; render FPS（引擎对象内缓存）
00583A3C  fmul    dword_B6FC0C                ; * gameSpeed
00583A42  fdivr   flt_BE51FC                  ; 1000 / (fps*speed)
00583A48  call    __ftol2                     ; 截断为整数毫秒
...
00583A77  push    0
00583A79  call    ds:__imp_Sleep              ; Sleep(0) 忙等
```

`1000 / renderFps` 的静态初始化在 `0xA010E1`：

```asm
00A010E1  mov     eax, 3E8h                  ; 1000
00A010E6  xor     edx, edx
00A010E8  div     dword_B72AE0               ; / render FPS
00A010EE  mov     dword ptr dbl_BF22F8+4, eax ; 存成 double 的整数部分（帧毫秒）
```

### 3.3 每帧更新 `sub_570C79` 与 6 相逻辑调度

`sub_570C79` 是引擎的每帧 update，核心字段（`this` = GameEngine）：

| 偏移 | 含义 |
|---|---|
| `+0x40` | phase（1..6） |
| `+0x44` | frames-per-tick（renderFps / logicFps） |
| `+0x48` | **interp**（tick 内插值 0..1，渲染动画用） |
| `+0x4C` | “本帧刚开启新 tick”标志 |
| `+0x50` / `+0x54` / `+0x58` | FPS 采样计数 / 上次时间 / 实测 update FPS |

关键代码：

```asm
00570CD7  mov     ecx, [esi+40h]             ; phase
00570CDA  cmp     ecx, 6
00570CDD  jnz     short loc_570CF9
00570CDF  cmp     byte ptr [esi+4Ch], 0      ; 新 tick 标志
00570CE3  jz      short loc_570CF9
00570CE5  mov     eax, dword_B72AE0
00570CEA  xor     edx, edx
00570CEC  div     dword_B72ADC               ; eax = renderFps / logicFps
00570CF2  mov     byte ptr [esi+4Ch], 0
00570CF6  mov     [esi+44h], eax
00570CF9  lea     eax, [ecx+1]
00570CFC  mov     [esi+40h], eax
...
00570D9D  mov     edx, [esi]
00570D9F  push    eax
00570DA0  call    dword ptr [edx+94h]        ; 派发 phase（本版本 0x583577）
```

即：**每个逻辑 tick 分 6 个 phase**；phase 走到 6 后回绕到 1，并重新计算
`renderFps / logicFps`（原版 30/15 = 2 帧/tick）。`phase` 和 `interp` 也是动画插值的
信息来源。

### 3.4 为什么“直接把 30 改成 120”会让游戏快 33%

引擎在 `>= 90 FPS` 时的相位调度逻辑是“每次 update 只跑一个 phase，phase 6 后立刻开始
下一个 tick”，也就是 **6 个渲染帧 = 1 个逻辑 tick**。原版 30 FPS 时 6 帧 = 200 ms，正好
对应 15 Hz；到 120 FPS 时 6 帧只有 50 ms，于是逻辑变成 20 tick/s，比原版快 33%。
这正是网上很多“解锁 30 FPS”方案会整体加速的原因。

所以 120 FPS 的关键不是改常量，而是**把 tick 边界从“按帧数”改成“按真实时间”**。

## 4. 120 FPS 的实现方案

### 4.1 总体思路

1. **渲染侧**：把“读取渲染帧率”的指令操作数重定向到一块补丁内存，里面写 120。
   渲染帧率全局 `0xB72AE0` 本身仍保持 30（避免影响把它当“30 分之一秒”时钟的效果代码）。
2. **调度侧**：用 `timeGetTime` 以真实时间驱动 15 Hz tick（每 tick 66 ms，即 198 个
   1/3 ms 单位，匹配原版 66 ms 的实测 tick），每帧运行“到期的 phase”，并设置 `interp`。
3. **动画侧**：`interp = (now - tickStart + frameLength) / 200`，0..1 连续变化；配合 120
   渲染帧，模型在每 tick 内被采样 8 次，实现 120 FPS 动画而速度不变。
4. **效果/相机/2D 动画侧**：所有“按渲染帧计步”的效果（粒子、拖尾、淡入淡出、相机滚动、
   Anim2D、炮塔插值等）改成按 `30/fps` 缩放或改用 30 Hz 帧号，避免 4 倍速。

补丁是**运行时内存补丁**：`dinput8.dll` 代理被游戏从自身目录加载，托管 CLR 后调用
`CnCFpsUnlocker.dll`；后者读取磁盘 PE 做特征扫描，`VirtualAlloc` 0x2000 字节可执行内存，
写入 120、stub 和跳转，再恢复页面保护。磁盘上的 `cnc3ep1.dat` 一个字节都不改。

### 4.3 时间基准调度器（核心）

补丁把 `0x570CD7`（`mov ecx,[esi+40h] / cmp ecx,6`）和 `0x570DA6`（`mov ecx,[dword_BD4DAC]`）
替换为生成的两段 stub。stub 的逻辑等价于：

```
now3 = timeGetTime() * 3                 ; 1/3 ms
t    = now3 - tickStart
if (phase == 6 && pending) { tickStart += 198; pending = 1; }   // 新 tick
// 到期的 phase 数量 = 1 + floor(t * 6 / 200)
for (k = 1; k <= due; k++) {
    phase = k;
    interp = k/6;                         // 与原版相位值一致（避免联机不同步）
    dispatch(k);                          // vtable+0x94
}
interp = min(1, (now - tickStart + frameLength) / 200);   // 每帧连续插值
```

- tick 长度取 **198 个 1/3 ms = 66 ms**，对应原版帧限制器整毫秒截断后的实测 15.15 Hz；
- `frames-per-tick` 和 `cmp 6` 的读取被改成 `max(fps,90)` / `2*logic`，强制调度器保持
  “一次一个 phase”的模式，把批量调度交给时间 stub；
- 这样在 60/90/120/165 下逻辑都稳定在 15 Hz 左右，而不是 120/6 = 20 Hz。

### 4.4 插值（动画 120 FPS 的来源）

引擎的 `interp`（GameEngine + 0x48）在每个渲染帧被写成 0..1 的连续值：

- 120 FPS、15 Hz 时，每个 tick 有 8 个渲染帧，interp 依次约 1/8、2/8 … 8/8；
- 模型绘制用 `interp` 在上一逻辑帧与当前逻辑帧的骨骼/变换之间插值；
- 因此模型每秒被采样 120 次，但动画时间轴仍按 15 Hz 的逻辑 tick 前进，速度不变。

实测 5 秒内 `interp` 采样 278 次，出现 **63 个不同值**，范围 0 → 0.9697，说明插值在
连续变化而不是冻结/跳变。

### 4.5 效果时钟的修正（避免 4 倍速/闪烁）

SAGE 里“30”同时被当作两种东西：渲染帧率，以及粒子/特效的“1/30 秒”时间单位。
直接改渲染帧率会让粒子出生时间戳跑到 GPU shader 时钟前面，产生满屏白色/彩色闪烁。
补丁只重定向“节奏类”读取，保留所有 30 Hz 时间单位：

- `framesPerMs = fps * 0.001` 的初始化保持 30；
- 粒子管理器的 “now” 与 GPU shader 的 `Time` 保持 30 Hz 时钟；
- 粒子模拟调用被节流到 30 Hz（本版本 `0x79DF11`）；
- 相机滚动、相机按键缩放/旋转、淡入淡出、拖尾、炮塔插值、2D 动画（Anim2D）、
  漂字、闪烁等按 `30/fps` 缩放或换算成 30 Hz 帧号。

## 5. 运行验证

### 5.1 A/B 计时方法

用 Frida 在游戏进程内挂两个计数点：

- `0x570C79`（引擎每帧 update）→ 渲染帧数；
- `0x583577`（phase 派发函数，vtable+0x94）→ 每 tick 调用 2 次（批量模式：
  phase 1-3 一次、4-6 一次），所以 `ticks = calls / 2`。

### 5.2 测量结果

| 场景 | 采样窗口 | 渲染帧数 | 渲染 FPS | 派发调用 | 逻辑 tick/s |
|---|---|---|---|---|---|
| 原版（补丁关闭，主菜单） | 5.000 s | 152 | **30.40** | 152 | **15.200** |
| 120 FPS 补丁（主菜单） | 5.001 s | 593 | 118.58 | 151 | **15.097** |
| 120 FPS 补丁（遭遇战内） | 5.001 s | 594 | 118.78 | 152 | **15.197** |
| 120 FPS drawfix（遭遇战内） | 5.002 s | 594 | 118.75 | 151 | **15.094** |

说明：

- Frida 的两个 `Interceptor` 钩子本身有每帧开销，所以进程内计数是 118.6～118.8；
  NVIDIA HUD 在同样场景显示 **120**（见截图）。
- 原版与补丁的逻辑 tick 速率差 **0.02%**（15.200 → 15.197），在采样误差内；
  游戏内单位移动、建造、开火、动画周期均按逻辑 tick 推进，因此速度不变。
- drawfix 版本复测：120 FPS 两次采样 118.75 / 118.35 FPS，逻辑 15.094 / 15.194 tick/s；
  `newtick 0x423CA2` 生效，`isNewTick` 返回 yes 约 59～61 次/秒（修复前为 0）。
  60 FPS 版同样复测 59.78 FPS / 15.194 tick/s。
- 静态逻辑帧率仍为 15，渲染帧率全局仍为 30；被重定向的是代码里的操作数。

## 6. Anim2D 与“缺失项”分析

补丁日志的 `missing` 列表是“本版本没有命中对应特征”的意思，不等于功能缺失。逐项核对：

| 缺失项 | 分析 |
|---|---|
| `anim2d` | 本版本的 `Anim2D` 不是上游标准形态（`mov reg,[reg+74h]`），而是 `mov ecx,[0xBDD638] / mov eax,[ecx] / call [eax+78h]`。但 `fxframes`/fx 修复（patch+0xD00 的 stub）已经覆盖了这两处 `call [eax+78h]`（`0x5D3718`、`0x5D7F7E`），stub 内容为 `getFrame*30/fps`。我已用 Frida 读取确认：两处均跳到 `patch+0xD00`，stub 字节为 `8B 01 FF 50 78 6B C0 1E ...`。因此 Anim2D 已被正确换算为 30 Hz 帧号，**不存在 4 倍速**。 |
| `construction` | 上游该项针对 RA3 的 `StructureUnpackUpdate`（苏/帝国建造进度）代码形态；KW 1.0 没有该形态。KW 的建造进度走逻辑 tick，不需要该修复。 |
| `zoom` | RA3 专用相机拉远。 |
| `traillock` | RA3/Uprising 的拖尾顶点锁。 |
| `sway` | RA3/Uprising 的车辆/船只弹簧摆动。 |
| `pulse` | RA3 技能放置圈脉动。 |
| `topple` | RA3/Uprising 的路灯/静态物倒下混合。 |

我们另外做过一个实验性 `Anim2D` 补丁（修改 `Unlocker.cs`，在 `0x5D3712`/`0x5D7F78`
写入完整 stub），但运行验证发现它和 fx stub 重叠、造成重复换算；由于 fx 修复已经正确，
该实验补丁**未包含在交付版本**中。交付版本基于上游 v1.9.5，并额外包含 1.0 的
`newtick` split 修复（`1.9.5-kw1.0-drawfix`，SHA-256 `D2C1979A...`）；
它与发布包不再逐字节相同，修复说明见 [`修复说明-单位不显示.md`](修复说明-单位不显示.md)。

**安装**：把 `bin\` 三个文件复制到 `RetailExe\1.0\`（`cnc3ep1.dat` 同目录），正常启动。
**卸载**：删除这三个文件，游戏恢复 30 FPS。

补丁不写游戏文件、不联网；只在进程内改内存。上游为 GPLv3，源码与许可证已一并提供。

## 8. 限制与风险

1. **帧率上限**：必须是 15 的倍数；工具会把目标帧率限制到显示器刷新率向下取整的
   15 倍数。165 Hz → 120 可行；60 Hz 屏只能 60。
2. **性能不足时**：如果机器跑不到 120，游戏仍按 15.1 tick/s 正常运行（不会慢放/加速），
   只是画面没那么平滑。
3. **版本/模组**：本报告与验证针对 `1.0.2955.37387`。补丁按指令形态扫描，其他版本
   可能命中不同；启动日志 `SAGEUnlocked.log` 会列出 found/missing。
4. **联机**：未测试多人同步；单机战役/遭遇战已验证。补丁不改变逻辑步进顺序（phase
   内插值与原版一致），但联机使用需自行评估。
5. **DRM/反作弊**：游戏为 2008 年 SecuROM 版本；本机以现有启动方式运行正常。补丁只
   改内存，不修改受保护文件。
